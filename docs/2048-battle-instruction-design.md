# 2048 对战版 · 指令设计流程复盘

> 用 Vibe Coding 方式，把「双人轮流对战版 2048」这类变体需求，拆成可判定的 Spec，再用分步指令驱动 AI 生成、跑验收、按 Bad Case 迭代。
>
> - 可玩 Demo：`/2048-battle/`（本仓库内，HTML5 单文件，无外部依赖）
> - 技术形态：原生 HTML / CSS / JS，键盘操作，桌面端
> - 交付周期：约 1 小时，指令迭代 7 轮，含 2 个 Bad Case 修复
> - 质量：35 条逻辑回归用例通过

---

## 1. 为什么先写 Spec 再写指令

「做个双人对战 2048」这种需求直接丢给 AI，通常能跑，但很难验收——你不知道它到底算不算做对。

所以整个流程只做一件事：**把模糊需求翻译成「可以被自动判定对错」的验收标准**，再让 AI 一条一条满足。指令只是载体，验收标准才是真正的需求。

核心原则：

- **验收标准先行**：先写清楚"输入什么、必须输出什么"，再让 AI 写代码；
- **可判定**：每条标准都能用一组具体数据验证，而不是"看起来对"；
- **小步提交**：一次指令只推进一个可验收的小目标，跑通再进下一步。

## 2. Spec 拆解：功能清单 + 验收标准

### 2.1 功能清单

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| F1 | 双人独立棋盘 | 双方各有一块 4×4 棋盘与独立得分 |
| F2 | 回合制操作 | 玩家 1 方向键、玩家 2 WASD，轮流出手 |
| F3 | 标准 2048 合并 | 滑动 + 同值合并，每行每回合只合并一次 |
| F4 | 有效/无效移动区分 | 棋盘无变化视为无效，不结算回合 |
| F5 | 新块生成 | 每次有效移动后，在当前玩家棋盘生成 1 个新块（90% 为 2，10% 为 4） |
| F6 | 胜负判定 | 合成 2048 / 逼死对手 / 自灭，三种结局 |
| F7 | 结束与重开 | 结束弹层展示胜者与比分，可一键重开 |

### 2.2 可判定验收标准（节选）

| 用例 | 输入 | 期望输出 | 判定方式 |
| --- | --- | --- | --- |
| AC-01 | 单行 `[2,2,4,0]` 左移 | `[4,4,0,0]` | 精确相等 |
| AC-02 | 单行 `[2,2,2,2]` 左移 | `[4,4,0,0]` | 精确相等（两两合并，不连锁） |
| AC-03 | 单行 `[4,4,4,4]` 左移 | `[8,8,0,0]` | 精确相等 |
| AC-04 | 单行 `[2,4,2,4]` 左移 | `[2,4,2,4]` | 无相邻同值 → 不变 |
| AC-05 | 对 `[2,4,8,16]` 整行左移 | `changed === false` | 布尔判定，且不得生成新块 |
| AC-06 | 棋盘存在 `1024,1024` 且左移合并 | `new2048 === true`、该格 `2048` | 布尔 + 数值 |
| AC-07 | 合成 2048 的同时对手死局 | 判定为「合成 2048」胜 | 优先级判定 |
| AC-08 | 自己走完一步后自己死局 | 对手获胜（自灭） | 胜负归属判定 |
| AC-09 | 满盘但存在相邻同值 | `canMove === true` | 布尔判定 |
| AC-10 | 满盘且任意相邻都不同值 | `canMove === false` | 布尔判定 |

> 关键点：像 AC-01 这种「`[2,2,4]` 左移必须等于 `[4,4,0]`」的标准，把"合并规则"这种口头描述，变成了一个 AI 无法含糊糊弄的断言。

## 3. 分步指令设计

每轮指令都遵循同一个模板，只推进一个可验收的小目标：

```text
【目标】本轮只实现：<单一功能点>

【验收标准】
- 输入 <具体数据> → 必须输出 <具体结果>
- 边界：<无变化 / 满盘 / 大数合并 …>

【约束】
- 不实现：<本轮无关功能，明确排除>
- 不改动：<已完成且通过验收的部分>

【提交粒度】
- 跑通上述验收标准后再进入下一轮
```

### 7 轮迭代记录

| 轮次 | 本轮目标 | 验收标准 | 结果 |
| --- | --- | --- | --- |
| 1 | 页面骨架 + 双棋盘渲染 + 键盘映射 | 两块 4×4 网格渲染；方向键/WASD 被正确捕获 | 通过 |
| 2 | 单行滑动与合并算法 | AC-01 ~ AC-04 全部精确相等 | 通过 |
| 3 | 四方向 `move()` 封装 | 上/下/左/右映射正确，返回 `changed/gained` | 通过 |
| 4 | 回合流转 + 独立棋盘 + 新块生成 | 有效移动后切换玩家；无效移动不切换 | 部分 → 触发 Bad Case #2 |
| 5 | 三优先级胜负判定 + 结束弹层 + 重开 | AC-06 ~ AC-10 通过，优先级正确 | 通过 |
| 6 | 修复 Bad Case #1：连锁合并 | `[2,2,4,0]` 左移必须为 `[4,4,0,0]` | 修复并回归 |

## 4. 运行验收：35 条逻辑回归用例

把验收标准固化成回归用例，每次修改后整体重跑。用例按职责分组：

| 分组 | 条数 | 覆盖内容 |
| --- | --- | --- |
| 合并规则 | 12 | 相邻同值合并、单次合并、空位压缩、大数合并 |
| 方向与棋盘 | 8 | 上/下/左/右映射、得分累加、`changed` 计算 |
| 胜利判定 | 4 | 合成 2048、未达 2048、已有 2048 不重复触发 |
| 死局判定 | 6 | 有空格、满盘可合、满盘死局、竖向可合 |
| 回合经济 | 5 | 有效/无效移动、位置变化、回合不误切换 |
| **合计** | **35** | — |

代表性用例：

```text
[2,2,4,0] 左移  → [4,4,0,0]      // 防止连锁合并
[2,2,2,2] 左移  → [4,4,0,0]
[4,4,4,4] 左移  → [8,8,0,0]
[2,4,2,4] 左移  → [2,4,2,4]      // 无合并不变
[2,4,8,16] 左移 → changed=false  // 无效移动
```

> 实现上，`slideRowLeft()` 合并后用一次 `i++` 跳过被合并的块，保证「同一行每回合只合并一次」。这一行就是 Bad Case #1 的修复点。

## 5. Bad Case 反馈式迭代

### Bad Case #1 · 连锁合并

- **现象**：`[2,2,4,0]` 左移，期望 `[4,4,0,0]`，实际却得到 `[8,0,0,0]`。
- **根因**：合并后没有跳过被合并的元素，新合成的 `4` 又与后面的 `4` 再次合并，等于"一回合合两次"。
- **修复**：合并命中时对循环变量额外 `i++`，跳过已参与合并的块。
- **回归**：把 AC-01/AC-02/AC-03/AC-09 加入回归集，确保任何方向的单行合并都只合并一次。

```js
if (i + 1 < tiles.length && tiles[i] === tiles[i + 1]) {
  out.push(tiles[i] * 2);
  i++; // 跳过被合并的块 —— 保证一次合并
} else {
  out.push(tiles[i]);
}
```

### Bad Case #2 · 回合经济

- **现象**：玩家朝一个走不动的方向按键，棋盘没有任何变化，却把回合交给了对手，还顺手给对手生成了一个新块。
- **根因**：早期版本把"按了一次方向键"当成一回合，而不是把"棋盘发生了实质变化"当成一回合。无效操作被计费，破坏了回合公平（回合经济失衡）。
- **修复**：以 `changed` 作为回合结算的闸门——无效移动只做抖动反馈，不切换玩家、不生成新块、不计分。
- **回归**：AC-05 + 回合经济 5 条用例，保证「无效操作零成本、有效操作才结算」。

```js
if (!result.changed) {
  // 无效移动：不轮换、不生成新块，只给抖动反馈
  shake(boardEls[playerId]);
  return;
}
// 仅在这里：更新棋盘、计分、生成新块、切换回合
```

## 6. 变体设计与取舍

### 6.1 新增玩法：回合制对战

原版 2048 是单人无限刷分。对战版改成**双方各持一块棋盘、轮流出手**：

- 玩家 1 用方向键，玩家 2 用 WASD；
- 只允许当前玩家操作自己的棋盘；
- 每次有效移动后，仅在自己棋盘生成 1 个新块。

### 6.2 胜负判定优先级

三种结局可能同时发生，必须定义优先级，避免"到底谁赢"的歧义：

```text
优先级 1：合成 2048          → 立即获胜（无论其它条件）
优先级 2：把对手逼入死局      → 获胜（对手棋盘无可行操作）
优先级 3：自己把自己走死      → 判负（自灭）
```

实现上严格按此顺序判定，所以「合成 2048 的同时对手死局」判为合成胜，「逼死对手的同时自己死局」判为逼死对手胜。

### 6.3 主动裁剪

为了让 1 小时内交付可玩版本，刻意砍掉：

- **滑动动画**：只保留合并/生成的最小动效（pop / appear），不做逐格位移动画；
- **触屏适配**：只做键盘操作，不做移动端滑动与响应式棋盘；
- **存档 / 悔棋 / AI 对手**：不在本次范围内。

取舍逻辑：先保证**规则正确 + 可玩闭环**，表现层与多端适配留到后续。

## 7. 沉淀：可复用的指令模板

把这次跑通的套路固化成一个模板，下次做别的变体可以直接套：

```text
1. 先把需求拆成功能清单，每条配一个「可判定」的验收标准（给具体输入/输出）。
2. 按验收标准排优先级，一次指令只做一条主线，明确写出「本轮不做什么」。
3. 每条标准落成一条回归用例，改完整体重跑，绿了才进入下一轮。
4. 出现 Bad Case：先定位根因（是哪条规则没被表达清楚），再修，再补回归用例。
5. 每一轮都是一次可回滚的小提交，而不是一次性的大爆炸。
```

这套「验收标准先行 + 小步提交」的流程，才是这次能在 1 小时内、用 7 轮迭代做出可玩对战版 2048 的真正原因。
